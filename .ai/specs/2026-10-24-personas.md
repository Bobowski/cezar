# Personas — named agents of a project, for workflow steps and dispatch

> Status: built (2026-10-25) on `brutus` — see §11 for where the build differs. Branch: `brutus`.
> Builds on: `packages/cezar/src/skills.ts` (discovery precedence, frontmatter), `workflows/types.ts`
> (a step's `runner`, `model`, `allowedTools`, `skill`), `2026-09-10-dispatch.md` (`cez task create
> --runner --model --tools`), `2026-07-29-agent-profiles.md` (accounts, which personas are not).
> Backlog item: "agents like `.claude/agents` — we create personas for the project".

## 1. Problem

"The reviewer is Opus with read-only tools and the review skill; the implementer is Codex with
the repo's conventions skill" is said again in every workflow step and every `cez task create`.
Claude Code has `.claude/agents/*.md` for this, but those files describe Claude's subagents:
one backend, Claude's tool names, invisible to Codex and OpenCode runs.

## 2. Decisions

| Question | Decision | Why |
| --- | --- | --- |
| Format | **cezar's own, `.ai/cezar/agents/<name>.md`** | Needs backend, cezar tool names, skills and a default workflow — more than Claude's frontmatter carries. |
| Where used | **Workflow steps (`agent: <persona>`) and dispatch children (`cez task create --as <persona>`)** | Not a composer picker (declined for now). |
| Claude's own files | Read-only awareness: a `.claude/agents` file is listed as "Claude-only" and usable as a persona on the Claude backend; nothing is rendered back | One source of truth. |

## 3. The file

```markdown
---
name: reviewer
description: Reads a branch against the base, writes findings, never edits.
runner: claude            # any RUNNER_IDS value; optional → project default
model: opus               # optional
allowedTools: [Read, Grep, Glob, Bash(git *)]   # optional; cezar's allowedTools grammar
skills: [code-review, repo-conventions]          # skill names from discovery
dispatch: { maxSubtasks: 0 }                      # optional defaults for children it may spawn
---
You are the project's reviewer. …                 # the system prompt body
```

Discovery: `.ai/cezar/agents/` (project, committable — the `.gitignore` allowlist), then
`~/.cezar/agents/` (global), then `.claude/agents/*.md` mapped (`tools` → `allowedTools`,
`model` kept, runner fixed to `claude`, marked `source: 'claude'`). Project wins by name.

## 4. Where it applies

- **Workflow step:** `agent: reviewer` on an agent step sets `runner`, `model`, `allowedTools`
  and prepends the persona body to the step's system prompt and its skills to the step's;
  explicit step fields override persona fields. `load.ts` checks the name at load
  time: a committed workflow naming an unknown one (perhaps a global persona this machine lacks)
  still loads, with a warning in `issues`, and that step fails when it runs; the save and
  inline-steps routes reject it (`stepsIssue`).
- **Dispatch:** `cez task create --as reviewer "<objective>"` fills the child's runner, model,
  tools and system prompt the same way; the engine's budget rules are unchanged. The parent's
  prompt lists the project's personas so an agent can choose one by name.
- **Cockpit:** Settings → project → **Agents** lists personas (name, description, runner,
  model, source), with an editor for the file (the Markdown editor Skills use) and a
  **New persona** form. The workflow editor's step form offers a persona picker.

## 5. Backend mapping

Claude: body as `--append-system-prompt`, tools as `allowedTools` (already honoured). Codex,
OpenCode, Cursor, Copilot, Junie, pi: body as the step's system prompt, model where the
backend takes one, tools ignored with the note the runner already emits for `allowedTools`
(AGENTS.md: only Claude honours them). Nothing persona-specific leaks past the runner seam.

## 6. API

```
GET  /agents                    → { personas: Persona[] }        (project-scoped, both mounts)
PUT  /agents/:name              { markdown }                      trusted operator
DELETE /agents/:name
```

Contract `agents.ts`: `personaSchema` with the frontmatter fields plus `source`.

## 7. Security

A persona is a system prompt and launch options committed in the repo — the same trust as a
skill or a workflow file. `allowedTools` can only narrow what the project already allows: it is
INTERSECTED with the list the step would otherwise run with (its own `allowedTools`, else the
default), entry by entry (`Bash(git *)` fits inside `Bash`; a step's `bashAllowlist` stays the
bound for `Bash`). A `.claude/agents` file's `tools:` is treated the same way. `Task` (Claude's
sub-agents, also spelled `Agent`) is never granted to a persona-driven run, from the persona or
the step: dispatch is the budgeted, visible path — on Claude it is also DENIED (`--disallowedTools
Task,Agent`), since `dontAsk` still runs a `Task` that `--allowedTools` leaves out. What was refused
is a transcript note, at spawn and again on Continue. An intersection that leaves a step NO tools
fails closed: the workflow is a load issue (`stepsIssue`, graph issues), the step fails before
spawning, and a `--as` dispatch is refused with a 409 — an empty list must never reach a runner
that reads it as "the default set" (pi without `--tools`). The check runs after the backend's own mapping: pi drops a `bashAllowlist`-bounded Bash, so a persona that leaves pi only that is refused the same way, and the pi runner itself refuses to spawn on a list that maps to nothing.

## 8. Zero config

No personas → nothing changes anywhere. `.claude/agents` files are read, never written.

## 11. As built

- The Settings section is **Personas** (`/p/<id>/settings/personas`): the project's existing
  "Agents" section (providers, default runner, models) already owns that id and title.
- `GET /agents/:name` → `{ persona, markdown }` was added so the editor opens on the file as
  written (comments and unknown keys survive a save); `GET /agents` also carries `issues` (files
  that failed to load) and `editable`. Writes are trusted-operator only; a global or
  `.claude/agents` persona is never written or deleted. Tokens need `author`.
- `dispatch:` takes the composer intent's fields (`maxSubtasks`, `inFlight`, `runner`, `model`,
  `budgetUsd`); `maxSubtasks` counts the persona's run's OWN children and may be `0`.
- A persona's `model` follows its own runner only: a step (or `--runner`) that moves it to another
  backend gets that backend's default. Continue keeps the owning step's persona tools and prompt;
  the model on Continue is the run's, as it already is for a step's `model`.
- A persona missing at spawn or Continue fails the step — a reviewer must not silently run with
  the default tools. Tools on a backend that ignores `allowedTools` (all but Claude and pi) are a
  transcript note.
- `allowedTools` is intersected with the step's own list or the default (§7), never widening it,
  and read-only Ask tasks still win. A `.claude/agents` `tools:` list maps the same way, so a
  Claude subagent's `Task` or a tool cezar's default denies does not ride in; `--tools` on
  `cez task create --as` narrows too. `Task`/`Agent` are refused for every persona-driven run.
- Only the repo's `.claude/agents` is read, not `~/.claude/agents`.
