# Brief: per-provider integration specs (2026-10-22)

Shared instructions for the tasks writing the provider specs under the umbrella [integration-providers](../2026-10-22-integration-providers.md).

CONTEXT: The umbrella design is committed at .ai/specs/2026-10-22-integration-providers.md — READ IT FIRST and treat it as binding (provider manifest, facets, anchors remote|scope, connection strategies cli|token, contract/routes, Issues view with provider switcher, several integrations per project, run-bookkeeping reference patterns, cross-provider linking, automations facet, phasing). Also read root AGENTS.md (zero-config, HTTP contract rules), docs/adding-issue-tracker.md, docs/issue-trackers.md, .ai/specs/2026-09-18-jira-linear-tracker-browsing.md, and the existing code seams: packages/cezar/src/server/forge/ (types.ts, github.ts, index.ts), packages/cezar/src/server/tracker/ (types.ts, jira.ts, linear.ts, transport.ts, connections.ts), packages/contract/src/{github,tracker,automations,health}.ts, packages/cezar/src/automations/ (github-poller.ts, tracker-poller.ts, event-source.ts), packages/web/src/routes/{github,tracker}/. Existing GitHub issue #847 has a detailed inventory of GitHub coupling — read it with `gh issue view 847`.

DELIVERABLE: exactly ONE new file (path below), a design spec in the style of other .ai/specs files (TLDR, problem, non-goals, vendor research, how it maps onto each facet of the umbrella seam, connection/auth, contract additions specific to this provider, UI specifics, automations events, run-bookkeeping reference patterns, cross-provider linking footer, dry-run fixtures, phasing/implementation steps naming concrete files, tests, backward compatibility, acceptance criteria, open questions). Keep it concise and concrete (~250–450 lines). Cite official docs URLs for every vendor claim. Clearly mark what you verified from docs vs. what is assumption. Do NOT edit any other file (if you think the umbrella spec needs a change, say so in your report's suggestions instead). Do NOT create GitHub issues or PRs, do not push. Commit your file on your branch with a message ending with the line: Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>

CLI RESEARCH IS REQUIRED: the owner wants integrations via the vendor's CLI where possible (cezar already delegates to `gh` so it never holds a credential). Use web search to research the current (2026) state of the vendor CLI(s): official vs community, maintenance status, install methods per OS (brew/apt/winget/npm), auth model and where credentials are stored, self-hosted/on-prem support, JSON output availability for each command you need, pagination, a raw API passthrough command (like `gh api`), rate limits, and gaps. Produce a command-by-facet mapping table (facet → exact CLI argv → JSON fields used), and a recommendation: cli, token, or both with preference order, with reasoning. Where the CLI is inadequate for a facet, specify the REST/GraphQL fallback endpoint.

When done, report with `node "$CEZ_BIN" task report --status done --result "..." --evidence "..." --suggestions "..."` including: the file path, the CLI recommendation in one line, and up to 5 suggestions for the umbrella spec.

NOTE (added after the first runs): WebSearch/WebFetch may be denied in your session. If so, fetch vendor docs with `curl -sL` (raw docs sources on GitHub/GitLab, official docs pages, package registries, `brew info`) and tag every claim [V] verified-today vs [A] assumption. Do not cite from memory as if verified.
