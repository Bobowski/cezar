# Easy MCP — a catalog, one click, every agent; committed or private

> Status: built (2026-10-25) on `brutus`. Branch: `brutus`.
> Builds on: `2026-10-07-private-project-mcp.md` (`.ai/cezar/mcp.local.json`, injected per
> agent at launch through each backend's own channel — `core/private-mcp.ts`),
> `2026-07-16-agent-config-files.md` (Settings → Agent config, the MCP sub-section per agent),
> `2026-10-21-env-references.md` (`${{ … }}` references), the project secrets store
> (`contract/secrets.ts`).
> Backlog item: "easy MCP".

## 1. Problem

Adding an MCP server to the agents cezar runs means knowing the server's command and env,
editing a JSON file in Agent config or `mcp.local.json` by hand, pasting a key into it, and
doing it again per project. The private file already solves "once for every agent, never
committed"; what is missing is the catalog, the click, the secrets, and a committed variant a
team can share.

## 2. Decisions

| Question | Decision |
| --- | --- |
| What "easy" means | **All three**: a catalog with one click; one definition rendered to every agent; a committable per-project file. |
| Catalog source | **A curated list in cezar plus search of the official MCP Registry.** |
| Where a definition lands | **Chosen when adding: project (`.ai/cezar/mcp.json`, committed, secrets as references) or private (`mcp.local.json`).** |

## 3. Behaviour

**Settings → project → MCP servers** (a new section; Agent config keeps the raw per-agent
files for what is not cezar's):

- Two lists, **Project** (`.ai/cezar/mcp.json`) and **Private** (`mcp.local.json`), each row: name,
  transport, status (last launch injected / failed with reason, from the run notes), the agents
  it reaches (every backend with a launch-time channel; Cursor and pi get the existing note).
- **Add from catalog** opens a sheet: the curated list (Context7, Playwright, GitHub, Supabase,
  Vercel, Stripe, Sentry, Linear, Jira, Postgres, Filesystem, Fetch, Memory…; each entry knows
  its command/URL, the env or header names it needs, and a docs link), and a search box over
  the MCP Registry (`registry.modelcontextprotocol.io`, read-only, results marked
  "unreviewed"). Picking one shows its required keys; each key is a **project secret** picker
  (existing store, or paste to create one) and the definition stores `${{ secrets.KEY }}`,
  never the value. Then **Project or Private**, then Add.
- **Add manually**: the JSON block, same two destinations.
- **Test** runs the server once with a 10 s budget (`initialize` + `tools/list`) and shows the
  tool names — the one place cezar talks to a server itself.
- The committed file is seeded into worktrees like other `.ai/cezar` content? No: like
  `mcp.local.json` it is read from the repo root at launch and injected, so a worktree never
  holds it and an agent cannot change its own servers.

**Rendering.** At launch, `private-mcp.ts` merges `mcp.json` (project) then `mcp.local.json`
(private wins per name — but over an approved project server only once confirmed, §5), resolves `${{ secrets.X }}` through the secrets store (audience
`cezar`), and injects through the existing per-backend channel. Nothing new per backend.

## 4. API

```
GET    /mcp                         → { project: McpServer[], private: McpServer[], catalog: CatalogEntry[] }
PUT    /mcp/:scope/:name            { definition }     scope: project | private
DELETE /mcp/:scope/:name
POST   /mcp/:scope/:name/test       → { ok, tools: string[] } | { ok: false, reason }
GET    /mcp/registry?q=             → { items: RegistryEntry[] }   (proxied, cached 1 h)
```

Project-scoped, both mounts. Writes are trusted-operator (they define code the agents run).

As built, the family is **`/mcp-servers`**, not `/mcp`: `/api/v1/mcp` is cezar's own MCP endpoint
(`2026-10-24-cezar-mcp-server`), and a project route of that path would collide with it. PUT and
DELETE answer the listing; the listing also carries `problems` per file and `editable`; the
registry answer carries `available`/`reason`. Literal env and header values are never served —
only `${{ secrets.X }}` references. API tokens: `author` reads the listing and the registry
search (a definition is a command), only `admin` writes and Tests. Each launch's per-server
outcome is indexed in the git-ignored `.ai/cezar/mcp-status.json` for the status column. A fork's
head (`untrustedHead`) gets no secrets here either: a server that references one is skipped — and
no project server at all (§5).

As built after review (2026-10-25): `POST /mcp-servers/approval` `{ hash, bindings }` approves the
committed file's current content (§5); the listing carries `approval` (`state`, `hash`, `changes`,
`bindings`) and each project row `boundSecrets`. `args`, `url` and `command` are served redacted —
a credential-named flag's value, URL userinfo, credential-named query values — except to the
operator or an `admin` token on a trusted cockpit. A literal env or header value in the `project`
scope is a 400 (use a reference, or Private); the manual sheet starts on Private.

## 5. Security

**Approval of the committed file (as built 2026-10-25).** `mcp.json` is repo content: nothing in it
runs or receives a secret until the operator approved THAT content on THIS machine, mirroring
Claude's own `.mcp.json` trust prompt.

- An approval records the file's content hash (sha256 of its exact bytes), the approved server
  entries (for the next review's diff) and, per server, the secret names it may receive —
  `{ server: [names] }`. It lives in `~/.cezar/mcp-approvals.json` (`0600`), keyed by checkout,
  never in the repo: an ignored file can still be force-added to a commit, a home file cannot.
- At launch the gate reads the file once; a project server is injected only when that text's hash
  is approved, and asks the store only for its bound names. An unbound reference is never
  resolved: that server is skipped with a run note. Any change to the file — an edit, a pull, the
  auto-sync fast-forward — drops the approval; nothing but the operator's Approve click and their
  own Settings write records one.
- Settings shows "Changed — review and approve" (or "Not approved yet") with a redacted diff of the
  server entries, a checkbox per secret reference, and **Approve** (trusted operator), which names
  the reviewed hash so a file that changed since is refused (409). A Settings PUT/DELETE of the
  project file keeps an approved or empty file approved, binding that entry's own references; a
  file still awaiting review stays awaiting it.
- A fork's head never gets project servers. Test of a project server uses only its bound secrets.
- A git-tracked `mcp.local.json` contributes no server (run note + a Settings warning), like the
  worktree scripts of a tracked `config.json`: a force-added file arriving by pull would otherwise
  run, with secrets, unapproved. A private server named like an APPROVED project server is skipped
  until the operator confirms in Settings that this entry (by its hash, kept in
  `mcp-approvals.json` under `overrides`) replaces it — any edit of the entry asks again.
- OpenCode takes launch-time servers only through `OPENCODE_CONFIG_CONTENT`, which every shell the
  agent runs inherits, so a server with resolved secrets is withheld from OpenCode with a note.
- Test scrubs literal env/header values from its reasons, caps unread stdout at 64 KiB, and
  follows redirects (and an SSE `endpoint`) only within the configured URL's origin.
- A registry entry holding `${{` anywhere it would launch is not launchable, and every reference in
  a translated definition is a key cezar declared.

- Secrets never enter either file; references resolve at launch, in memory, into the
  backend's own channel (a `0600` temp file for Claude, config overrides for Codex…).
- Registry results are data: an entry is added only when the operator picks it, and its
  command is shown before Add.
- `Test` runs the server as the cezar user with the resolved env, for 10 s, in a temp cwd.
- The project file is committed by the user, like workflows — the `.ai/cezar/.gitignore`
  allowlist keeps `mcp.json` committable and `mcp.local.json` ignored.

## 6. Zero config

The registry search is a network call made only when the operator types in the search box.
Everything else is files cezar already reads.

## 7. Not done here

- Writing the agents' native files (`.mcp.json`, `config.toml`) — Agent config still edits them raw.
- Per-task MCP (a server for one run only).
- OAuth-flow MCP servers that need a browser round trip at launch.

## 8. Verification

- Unit: approval gate (unapproved / changed → not injected; bound names resolved; unbound →
  skipped, never asked; a fast-forward approves nothing), merge order (private wins), reference
  resolution (missing secret → note, not crash),
  catalog entries validate against the definition schema, registry proxy caching and the
  "unreviewed" flag, `.gitignore` allowlist includes `mcp.json`.
- Agent env tests per backend already exist for `mcp.local.json`; extend with a project entry.
- VPS: add Context7 to Project with no secrets and Stripe to Private with `STRIPE_SECRET_KEY`
  from secrets; a Claude task and a Codex task both list the tools; `git status` shows only
  `mcp.json`.
