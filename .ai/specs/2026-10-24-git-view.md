## 1. Problem

`/p/:id/repo` has Changes, Commits, Branches (with tracking), Files and a sync bar. What it
cannot do: show how branches relate (which task branch sits where, what is merged), act on a
branch (checkout, merge, rebase, delete, compare), stage part of a change, or say which remote
a branch lives on when there are several. Each of those is a terminal today.

## 2. Decisions

| Question | Decision | Why |
| --- | --- | --- |
| Missing pieces | **Commit graph, branch actions, stage/unstage and partial commits, explicit remotes** | All four named by the owner. |
| Many checkouts (VPS, PC, PC2) | **One checkout per cezar; `origin` is the truth** | The hub model: other machines are browsers. Cross-checkout state is the multi-cezar spec's problem. |

## 3. Behaviour

### 3.1 Graph

A **Graph** tab: `git log --graph`-equivalent rendered as lanes (one SVG column, rows virtualised),
newest first, for `HEAD`, every local branch, every remote-tracking branch of every remote, and
every task branch (`cez/*` or the namer's name) — task branches labelled with their task title
and status (from the run index, the way `worktreeInfoSchema` already joins them). Filters:
mine · all remotes · tasks only; a search box over subjects and shas. Clicking a commit opens
the existing commit view (`/repo/commit/:sha`); clicking a label selects the branch for §3.2.
Merged task branches are drawn faded. The base branch's merge-base with each visible branch is
marked, because "where did this fork" is the question the owner asks most.

### 3.2 Branch actions

On a branch (Branches tab or a graph label): **Checkout** (the main checkout; refused with the
reason when the tree is dirty or a worktree-off task is running — trunk-based spec), **Merge
into current** (refused on a dirty tree too, naming the files), **Rebase current onto**, **Compare with current** (opens Changes anchored at the
merge-base, through `resolveTaskDiffBase`'s logic), **Delete** (local; and remote with a second
confirm), **Rename**, **Push to…** (pick a remote, §3.4), **Cherry-pick** on a commit. A
merge or rebase that stops on conflicts leaves git's state as is and shows the conflicted
files in Changes with **Abort** and **Continue** buttons; the editor opens the file with the
markers. No automatic resolution.

### 3.3 Staging

Changes gains the index: files move between **Staged** and **Changes** (`git add` / `restore
--staged`), a hunk gutter action stages or unstages a hunk (`git apply --cached` of the hunk
patch, the way the editor already produces hunks), **Discard** a file or hunk with a confirm.
Commit commits the index only; **Amend** rewrites the last unpushed commit (refused when it is
on the upstream); **Stash** / **Pop** with a list. The trunk-based **Commit to base** button
keeps its meaning: it lands the whole tree, whatever is staged (§4).

### 3.4 Remotes, explicit

A **Remotes** block on the Branches tab: every remote, its URL, which one is the PR target and
which the push default (as `resolveTaskRemotes` resolved them, with the reason: `gh repo
set-default`, fork parent, `pushDefault`), and per branch where it exists (`origin/x`,
`upstream/x`). **Fetch** per remote; **Push to…** names the remote. Adding or removing a remote
stays in the terminal — it is a configuration decision.

## 4. API (project-scoped, both mounts, chained onto the `repo` family)

```
GET  /repo/graph?limit&after&filter          → { commits: GraphCommit[], refs: GraphRef[], next }
POST /repo/branch/:name/checkout | merge | rebase | delete?remote=1 | rename | push { remote }
POST /repo/commit/:sha/cherry-pick
POST /repo/merge/abort | continue
POST /repo/stage   { paths } | { path, hunk }       POST /repo/unstage  (same)
POST /repo/discard { paths } | { path, hunk }, confirm: true, untracked?   (409 without the confirm;
                   exact unstaged files only; an untracked one also needs untracked: true)
POST /repo/stash   { message? }   POST /repo/stash/:n/pop   GET /repo/stash
GET  /repo/remotes                               → { remotes: Remote[], prTarget, pushDefault, reasons }
POST /repo/remotes/:name/fetch
```

Built with three more routes the behaviour needs: `GET /repo/status` (the index: staged,
unstaged with untracked, conflicted paths, the operation in progress, whether HEAD is pushed —
not `/repo/index`, because the typed client spells a path's root `index`), `GET
/repo/compare?ref` (Compare with current, anchored by `resolveCompareBase` in `git-diff-base.ts`)
and `POST /repo/commit { message, amend? }` (commits the index only). A hunk is named by its
`@@ -a,b +c,d @@` header; the server recomputes the patch, so no client patch is ever applied.
A merge, rebase, cherry-pick or stash pop that stops on conflicts answers `200` with
`conflicts`, not a 409. Only the Git page's own Commit (`POST /repo/commit`, refused while an
in-place task works in the checkout) commits a partial index. A task's landing — the trunk-based
Commit, Finish, `CEZ:DONE`, and every retry of a failed one — always takes the whole tree, since
what the agent staged is incidental. Through MCP a branch name with a slash cannot be a path parameter (the catalog
refuses `/` in params), so those branches are reachable from the cockpit, not from a tool.

Every mutation runs `git` with the project's own identity (the checkout's config), reports
git's own message on failure (`{ error }`, 409), and rings the existing `repo-sync:<project>`
and checkout-watch topics so open views refresh. Names pass `isSafeGitRef`.

## 5. Security

- Hosted: all of it is trusted-operator (the signed-in owner on the VPS); on a local cockpit the
  machine is the perimeter, as for the terminal.
- Nothing force-pushes. `Delete remote` and `Discard` are the destructive two and carry confirms.
- Rebase and amend refuse to rewrite commits that are on an upstream.

## 6. Zero config

Nothing to set; remotes are read, never written.

## 7. Not done here

- Interactive rebase, bisect, reflog browsing, submodules.
- Adding remotes from the cockpit.
- Branch state from other machines (multi-cezar spec).
